# PhishLab 生产部署手册

适用于本发布包 `phishlab-release-YYYYMMDD.tar.gz`（私有化部署）。

## 1. 包内容

```
phishlab/
├── deploy/                 # docker-compose / nginx / server.Dockerfile / 镜像导入导出脚本
│   ├── server.Dockerfile   # 构建时 --find-links=server/vendor/wheels 优先命中离线 wheel
│   └── license/            # vendor_public.pem（License 验签公钥；私钥绝不随包）
├── server/                 # 后端：FastAPI 核心服务 + Celery Worker/Beat + track/landing 边缘服务
│   ├── .env.example        # 环境变量模板（生产改名为 .env 后逐项配置）
│   ├── vendor/wheels/      # Python 依赖离线 wheel（cp311，目标机无需外网，见《离线交付说明.md》）
│   ├── alembic/            # 数据库迁移
│   ├── scripts/            # seed_admin.py（超管初始化，备用）
│   └── app/                # 业务模块
├── web/                    # 前端源码（node_modules 不打包；dist/ 为已构建产物）
└── docs/                   # 部署手册.md / 离线交付说明.md
```

> 目标机完全离线时，基础镜像（mysql/redis/minio/nginx/python:3.11-slim）需另从联网机器导出
> `images.tar` 导入——见《离线交付说明.md》§2（`deploy/export-images.sh` / `deploy/load-images.sh`）。
> `server` 镜像在目标机 `docker build` 产出，不需打包。

## 2. 环境要求

- Linux x86_64（Ubuntu 22.04+/Debian 12+ 均可），Docker Engine 24+ 与 Compose v2
- 资源建议：4C8G 起步（server + 2×worker + beat + track + landing + mysql + redis + minio）
- 演练规模 > 1000 目标时，worker 副本数与 MySQL 内存按规模上调

## 3. 域名规划（红线：隔离）

| 用途 | 示例域名 | 指向服务 | 要求 |
|---|---|---|---|
| 主平台（前端+管理 API） | `admin.example.com` | nginx → server:8080 | HTTPS |
| 追踪域 | `t.example.com` | track:8081 | HTTPS；**独立域名，禁止与主平台同域同 IP** |
| 演练落地域 | `p.example.com` | landing:8082 | HTTPS；独立域名，可配置域名池轮换；落地页可配自定义路径直挂根路径（§6.1） |

追踪/落地与主平台同域同 IP 会破坏"仿真度"与隔离红线，验收时视为不通过。

## 4. 部署步骤

### 4.1 解包与配置

```bash
# 包为平铺结构（根含 server/ web/ deploy/ docs/），解到独立目录后进入
mkdir phishlab && tar -xzf phishlab-release-YYYYMMDD.tar.gz -C phishlab   # 换成实际日期
cd phishlab
cp server/.env.example server/.env
vi server/.env   # 逐项按下面"必改项"配置
```

**`server/.env` 必改项**：

```ini
# 1) JWT 签名密钥：随机生成 ≥32 字符，丢失后所有会话失效
SECRET_KEY=$(openssl rand -base64 48)

# 2) 敏感字段 AES-GCM 密钥：生产必须显式配置（丢失后历史口令密文不可解密！）
AES_KEY_B64=$(openssl rand -base64 32)

# 3) 数据库/Redis/MinIO 连接串（按实际部署改账号密码）
DATABASE_URL=mysql+pymysql://phishlab:改我@127.0.0.1:3306/phishlab?charset=utf8mb4
REDIS_URL=redis://127.0.0.1:6379/0
MINIO_ENDPOINT=127.0.0.1:9000
MINIO_ACCESS_KEY=改我
MINIO_SECRET_KEY=改我

# 4) 追踪/落地独立域名（与第 3 节一致）
TRACK_BASE_URL=https://t.example.com
LANDING_BASE_URL=https://p.example.com

# 5) CORS 白名单：生产收紧为前端域名（JSON 数组）
CORS_ORIGINS=["https://admin.example.com"]

# 6) ChatBI 独立只读账号（红线 5，生产必配）：专用只读 MySQL 账号，
#   与主库写账号分离；未配置时兜底主库连接 + 事务级只读（START TRANSACTION READ ONLY）
CHATBI_READONLY_DSN=mysql+pymysql://phishlab_ro:改我@127.0.0.1:3306/phishlab?charset=utf8mb4
```

> 只读账号授权示例：`GRANT SELECT ON phishlab.* TO 'phishlab_ro'@'%' IDENTIFIED BY '改我';`
> ChatBI 所有问数 SQL 均经表白名单 + 结构化校验 + 数据权限注入 + 审计留痕（审计动作 `chatbi_ask`）。

> MinIO 目前仅接入配置（附件载荷等功能未启用），但编排已含该服务，保持运行即可。
> compose 内 `server`/`worker`/`track`/`landing` 会用环境变量覆盖 DB/Redis 指向容器内网地址，`.env` 里其余项按上表填写。

### 4.2 修改编排内默认口令（deploy/docker-compose.yml）

```yaml
mysql:    MYSQL_PASSWORD / MYSQL_ROOT_PASSWORD / healthcheck 里的 root 密码
minio:    MINIO_ROOT_PASSWORD
```

### 4.3 启动

```bash
cd phishlab
docker compose -f deploy/docker-compose.yml up -d --build
docker compose -f deploy/docker-compose.yml ps   # 全部 running/healthy
```

### 4.4 初始化数据库（一次性）

```bash
docker compose -f deploy/docker-compose.yml exec server alembic upgrade head
```

### 4.5 初始化超管账号

二选一：

```bash
# 方式 A（推荐）：调用首启引导接口
curl -X POST http://<主平台IP>:80/api/v1/auth/init \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"强口令!","real_name":"超级管理员"}'

# 方式 B：容器内脚本（默认 admin / PhishLab@2026，登录后立即改密）
docker compose -f deploy/docker-compose.yml exec server python scripts/seed_admin.py
```

### 4.6 验证

```bash
curl http://<主平台IP>/api/v1/health        # {"code":0,...}
curl -I http://<主平台IP>/                   # 前端 index.html
# 浏览器打开 https://admin.example.com → 超管登录 → 建部门/通道/模板后发起一次「测试发送」
```

### 4.7 前端部署说明

**前端不需要单独部署**——`web/dist/` 已构建好打进本包，`deploy/docker-compose.yml` 的 nginx 容器以只读卷挂载它：

```yaml
nginx:
  volumes:
    - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
    - ../web/dist:/usr/share/nginx/html:ro   # 相对 deploy/ 目录 → phishlab/web/dist
```

前端请求的分流（`deploy/nginx.conf`）：

| 路径 | 处理方 |
|---|---|
| `/`（index.html + assets） | nginx 静态直出，`try_files $uri $uri/ /index.html` 兜底 SPA 路由（刷新/直达二级路由不 404） |
| `/api/`、`/static/`、`/report/` | 反代到 server:8080 |

前端产物使用**相对路径 `/api`**，部署在任意域名下都无需重新构建。

**仅更新前端**（后端不动时）：在任一台有 Node 的机器上 `cd web && npm install && npm run build`，把新 `web/dist/` 覆盖到服务器同目录，然后：

```bash
docker compose -f deploy/docker-compose.yml restart nginx
```

只换 Logo 等平台静态文件：`server/static/` 挂的是 `static_data` 命名卷（server/worker 共享，附件投递依赖它），用 `docker cp 新文件 phishlab-server-1:/srv/phishlab/server/static/...` 或 `docker compose exec server` 进容器替换（`/static` 已配 no-cache，替换即生效）。**不要**用 `docker compose down -v`，会连同附件/上传文件一起清掉。

## 5. 无 Docker 环境部署（裸机）

适用于无法使用 Docker 的服务器（如客户内网裸机）。与容器部署的区别只有进程管理方式：本机 Python venv + systemd 托管五个进程（server/worker/beat/track/landing），MySQL/Redis 用本机服务，前端仍由 Nginx 托管。**static 附件目录在裸机下天然同机同路径，无容器共享卷问题**。

### 5.1 前提组件

| 组件 | 要求 | 说明 |
|---|---|---|
| Python | 3.11+ | `python3.11 -m venv` |
| MySQL | 8.0 | 本机或远端均可 |
| Redis | 7.x | 本机或远端均可 |
| Nginx | 任意较新版 | 前端静态 + 反代 |
| MinIO | 可暂不装 | 当前版本未接线（见 §4.1 说明） |

### 5.2 建库建号

```sql
CREATE DATABASE phishlab CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'phishlab'@'%' IDENTIFIED BY '<强密码>';
GRANT ALL PRIVILEGES ON phishlab.* TO 'phishlab'@'%';
-- ChatBI 只读账号（红线 5，生产必配）
CREATE USER 'phishlab_ro'@'%' IDENTIFIED BY '<强密码>';
GRANT SELECT ON phishlab.* TO 'phishlab_ro'@'%';
```

### 5.3 解包、建 venv、离线装依赖

```bash
mkdir phishlab && tar -xzf phishlab-release-YYYYMMDD.tar.gz -C phishlab
sudo mv phishlab /opt/ && sudo chown -R <运行用户> /opt/phishlab
cd /opt/phishlab/server
python3.11 -m venv .venv
.venv/bin/pip install --find-links=vendor/wheels \
  fastapi "uvicorn[standard]" sqlalchemy alembic pymysql cryptography \
  pydantic pydantic-settings email-validator redis celery httpx sse-starlette \
  pyjwt aiosmtplib dnspython exchangelib minio openpyxl python-multipart \
  sqlglot qrcode pillow
```

### 5.4 配置 .env（同 §4.1）

```bash
cp .env.example .env && vi .env
```

必改项与 §4.1 完全一致（SECRET_KEY / AES_KEY_B64 / DATABASE_URL / REDIS_URL / 域名 / CORS）。裸机下 DATABASE_URL 用 `127.0.0.1` 或 MySQL 实际地址即可。

### 5.5 迁移 + 初始化管理员

```bash
cd /opt/phishlab/server
.venv/bin/alembic upgrade head
.venv/bin/python scripts/seed_admin.py   # admin / PhishLab@2026，登录后立即改密
```

### 5.6 启动服务（systemd）

`deploy/systemd/` 下已备好五个单元文件，按实际路径改 `ExecStart`/`WorkingDirectory`（默认 `/opt/phishlab/server`）与运行用户后：

```bash
sudo cp deploy/systemd/phishlab-*.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now phishlab-server phishlab-worker phishlab-beat \
                              phishlab-track phishlab-landing
```

| 服务 | 进程 | 端口 | 说明 |
|---|---|---|---|
| phishlab-server | uvicorn app.main:app | 8080 | 主平台 API |
| phishlab-worker | celery -A worker worker | - | 投递引擎 + 事件消费 |
| phishlab-beat | celery -A worker beat | - | 定时调度，**必须单实例** |
| phishlab-track | uvicorn track.main:app | 8081 | 追踪服务（像素/跳转/beacon） |
| phishlab-landing | uvicorn landing.main:app | 8082 | 落地页服务 |

> 日志：`journalctl -u phishlab-worker -f`。升级时五个服务全部 `restart`（与容器版"worker/beat 必须重建"同理，旧进程不加载新代码）。

### 5.7 Nginx

直接用 `deploy/nginx.conf`，仅需把 `proxy_pass` 里的容器服务名换成本机端口：

```
# 主站（SPA + API）
proxy_pass http://127.0.0.1:8080;    # 原 server:8080
# t/p 独立域名 server 块
proxy_pass http://127.0.0.1:8081;    # 原 track:8081
proxy_pass http://127.0.0.1:8082;    # 原 landing:8082
```

t/p 域名块与证书要求见 §6。

### 5.8 验证

与 §4.6 相同：登录 → 建通道/模板 → 测试发送 → 走一遍打开/点击/提交链路。

## 6. track / landing 独立域名接入

`deploy/nginx.conf` 末尾注释段给了示例 server 块。生产做法：

1. 三个域名 A 记录指向同一台（或不同）服务器——**主平台与 t/p 至少域名不同**；
2. 用现有 nginx（或独立 nginx 实例）为 `t.example.com`、`p.example.com` 各建一个 443 server 块，`proxy_pass` 到 `track:8081` / `landing:8082`；
3. 各配独立证书（Let's Encrypt 或内网 CA，**SAN 需覆盖对应演练域名本身**，见下）；
4. 落地页若用域名池，为每个演练域名重复建块，证书均需覆盖。

### 5.1 落地页自定义路径（仿真防识别）

落地页支持**干净 URL**：在模板模块创建落地页时可配置"自定义路径"（全局唯一，如 `/`、`/login.html`；留空 = 默认 `/p/{slug}`）。配成 `/` 后，目标员工访问 `https://p.example.com/` 根路径即呈现仿冒页，链接中不再出现 `/p/` 平台特征。

| 事项 | 说明 |
|---|---|
| 表单提交 | 提交端点跟随页面路径：根路径页提交到 `POST /submit`，`/login.html` 提交到 `POST /login.html/submit` |
| 未注册路径 | 一律 404——演练域名下任意路径不会渲染仿冒页 |
| 保留路径 | `/p/`、`/t/`、`/px/`、`/pa/`、`/learn/`、`/health` 前缀不可用作自定义路径 |
| 邮件链接 | `track_link` 关闭时直链自定义路径；开启时 `/t/{token}` 302 到自定义路径并带 token |
| 证书要求 | 演练域名根路径即页面本身，证书 **SAN 必须包含该域名**（不是只覆盖子域名或 `p.example.com` 之外的域名） |

nginx 侧无需额外配置——`location / { proxy_pass http://landing:8082; }` 会把根路径与自定义路径一并透传。

## 7. 上线前安全核查清单

- [ ] `SECRET_KEY`、`AES_KEY_B64` 已生成并妥善备份（AES 密钥丢失 = 历史口令密文无法解密）
- [ ] MySQL / MinIO 默认口令已改
- [ ] 超管初始口令已改；员工数据走授权演练流程（`auth_confirmed` 勾选强制）
- [ ] 前端域名已配置 HTTPS；`CORS_ORIGINS` 已收紧（不留 `*`）
- [ ] `t.*` / `p.*` 与主平台域名、IP 隔离（验收红线）
- [ ] 演练域名证书 SAN 覆盖域名本身（自定义路径 `/` 时根路径即页面，SAN 缺位会告警暴露）
- [ ] 宏/EXE 附件载荷能力保持默认关闭（License 未授权时）
- [ ] 数据留存期 `platform_setting.retention_days` 已按合规要求配置

## 8. 运维

```bash
# 日志
docker compose -f deploy/docker-compose.yml logs -f server worker beat track landing

# 备份（建议 cron 定时）
docker compose exec mysql mysqldump -uphishlab -p<密码> phishlab > backup_$(date +%F).sql
# redis 无持久化需求（缓存/队列，可重建）；minio 卷为对象存储，按备份策略处理

# 升级流程
# 1) 备份数据库 → 2) 停服务 → 3) 解包新版本替换代码 → 4) alembic upgrade head
# 5) 起服务 → 6) 跑一遍第 4.6 验证
# 注意：worker/beat 容器必须一并重建（up -d --build 会重建镜像）——
#   旧容器内长驻进程不会加载新代码，模型字段变更后会出现
#   "Unknown column" 类报错，演练卡在"发送中"。

# 常见问题
# - SSE 监控无数据：确认 nginx 对该 location 未开 proxy_buffering（配置已默认关闭）
# - 邮件发送失败：检查通道 SMTP 端口/SSL（465 SSL / 587 STARTTLS）与 DKIM 配置
# - Celery 任务不执行：确认 worker 与 beat 均在运行，Redis broker 可达
# - 演练一直显示"发送中"：先看 worker 日志有无 deliver_batch 异常（批次自愈
#   会顺延 5 分钟无限重试）；常见原因是 worker 跑的是旧代码（见升级流程注意）
# - 落地页/点击链接 502/500：确认 track/landing 容器内 DATABASE_URL 指向 mysql
#   容器内网地址（compose 已注入，勿在 .env 里改回 127.0.0.1）
```

## 9. 已知边界（本版）

- `web/dist` 已在打包时构建；如改前端源码需在 web/ 内 `npm install && npm run build` 后重新打包
- MinIO 业务接入（附件载荷等）为后续迭代，本期仅保持服务运行
- 落地页/追踪演示用 `landing_port` 直连逻辑保留，生产一律走独立域名
